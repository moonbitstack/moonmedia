struct pub(all) struct Pes

A packetised elementary stream packet: the frame, or the piece of a frame, that a stream carries (ISO/IEC 13818-1 §2.4.3.7).

The optional header is kept as bytes. It carries the timestamps a player needs and a dozen flags about how the frame may be decoded, which it does not; keeping the bytes means a packet read and written again is the same packet, and a caller that wants a timestamp reads it with pts.

  • stream_idInt32
  • packet_lengthInt32 The length the packet declares, header included. Zero means "until the next packet begins", which is what a video frame larger than a packet uses.
  • flagsInt32 The bits of the first flags byte: scrambling, priority, alignment.
  • timestamp_flagsInt32 The bits of the second flags byte: which timestamps are present.
  • headerBytes The optional fields, verbatim: timestamps and the rarer flags.
  • dataBytes
pub fn Pes::dts(self : Pes) -> Int64?

The decode time of the packet, when it differs from the presentation time.

pub fn Pes::encode(self : Pes) -> Bytes

Write the packet back.

pub fn Pes::new(stream_id : Int32, data : Bytes, pts? : Int64, dts? : Int64) -> Pes

A packet carrying data on stream_id, timed by pts and, when frames are reordered, dts.

A timestamp is in units of 1/90000 second and is written as 33 bits, which wraps after about 26 hours: a stream that runs longer counts in circles, which is why players compare timestamps rather than sort by them.

struct pub(all) struct ChunkReader

Reads chunks back into messages.

A chunk stream is stateful: after the first chunk of a message, the ones that follow only carry a few bytes of header, because the type, length and stream are still what they were. The reader keeps that state per chunk stream, which is why it has to see the bytes in order.

  • pending@buffer.Buffer

pub fn ChunkReader::push(self : ChunkReader, data : BytesView) -> Array[Message]

Add bytes and take out the messages they complete.

A message split across several reads is held until its last chunk arrives; a message larger than the chunk size is split by the sender and put back together here.

The chunk size is framing rather than content, so it is applied here, as the bytes are read: a message that announces a new size is followed by chunks that already use it, and a reader that waited for its caller to notice would mis-read every one of them.
